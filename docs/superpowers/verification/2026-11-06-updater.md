# Verifica — aggiornamento automatico

Data: 2026-11-06. Spec: `docs/superpowers/specs/2026-11-06-updater-design.md`.

## Cosa è stato misurato

App vera, build di release AppImage (Linux, Xvfb, tauri-driver), chiave dell'updater **di test**
generata per la prova e scartata (non è la chiave del progetto), manifest servito da
`python3 -m http.server` su 127.0.0.1 (`dangerousInsecureTransportProtocol` solo nella config di
prova, passata con `--config`).

1. **Percorso felice.** 3.0.0 installata, server con 3.0.1 firmata (`tauri signer sign`) e
   `latest.json` generato da `scripts/updater-manifest.mjs`:
   - primo avvio: modal "Check for updates automatically?" → "Yes, check automatically";
   - modal "ModbusTool 3.0.1 is available" con le note del manifest;
   - "Install and restart": scaricato l'AppImage (log del server), sostituito il file installato
     (sha256 uguale a quello della 3.0.1), app riavviata (la nuova istanza ha richiesto di nuovo
     `latest.json`, perché la scelta "automatico" è ricordata).
2. **Firma di un'altra chiave.** Stesso pacchetto firmato con una seconda chiave: notifica
   "Update failed: The signature was created with a different key than the one provided", file
   installato invariato (stesso sha256), app ancora in esecuzione.
3. **Unit test** (`updates.test.ts`): offerta e "Più tardi" per sessione, chiusura della risorsa
   superata, errori solo per i controlli manuali, persistenza della scelta, cadenza di 6 ore
   solo in automatico, arresto di master e slave prima dell'installazione, avanzamento, errore
   d'installazione recuperabile.

## Cosa NON dimostra

- MSI su Windows (`installMode: passive`) e `.deb` (`dpkg -i` con elevazione): non provati.
- Il workflow di release reale: la parte nuova (firma, `latest.json`, upload) girerà alla prima
  release con il secret `TAURI_SIGNING_PRIVATE_KEY` impostato.
- La chiave del progetto (ID minisign `0BF4CC90AAFB5C7B`, inserita il 2026-11-06) non ha ancora firmato una release: la prima prova reale è la prossima release.
